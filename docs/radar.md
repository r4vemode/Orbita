# ORBITA Radar

Radar — отдельный модуль корпоративных событий. Он определяет компанию, тип, значимость и возможное влияние сообщения, сохраняет источники и объяснение. Событие Radar не создаёт торговую идею, BUY/SELL или брокерскую заявку.

## Что работает локально

- Лента с поиском по тикеру, компании, ISIN и тексту; категории, важность, влияние, период и страницы результатов.
- Карточка события: объяснение, извлечённые данные, времена обработки, ссылки на источники и доступная реакция рынка.
- Каталог компаний и aliases, единый pipeline, дедупликация с несколькими источниками и группировка связанных событий. Повестка о дивидендах остаётся заседанием, а последующее решение — отдельным событием.
- Редакция Radar: ручное событие, исправление анализа, публикация/скрытие, отметка ошибочной классификации, дубля и объединение источников. Исходный анализ и журнал действий сохраняются.
- Независимые задания источников с повторными попытками, мониторингом и безопасными кодами ошибок.
- Обновление открытой ленты через SSE, персональные правила отслеживания и интеграция типа `RADAR_EVENT` в существующую доставку Telegram.
- Блок Radar в первом наборе функций лендинга. Его события, числа и задержка явно обозначены демонстрационными.

Рабочие корпоративные feeds, внешний AI, настоящие котировки и фоновый Web Push не подключены. Локальное объяснение строится по правилам; это указано в событии. Наличие флага или адаптера не означает подключение соответствующего провайдера.

## Быстро посмотреть

Нужен Node.js 22+, рекомендуется актуальный 24 LTS.

```sh
npm run beta:local
```

Учебная среда создаёт отдельную временную базу, четыре аккаунта и не менее 15 вымышленных событий Radar. Данные входа выводятся только в вашем терминале. Откройте `/radar.html` под Pro или администратором, `/radar-admin.html` — под администратором. По умолчанию Exclusive подключён отдельно и не включает Radar. Остановка учебного запуска удаляет только его временные данные.

Для сохранения собственных локальных правок используйте обычный запуск. Наполнение выполняется явно:

```sh
npm run seed:radar
npm start
```

`seed:radar` использует `ORBITA_DATA_DIR` либо приватную папку `data` проекта. Скрипт запрещён при заданном `ORBITA_PUBLIC_ORIGIN` или `NODE_ENV=production`, отказывается от каталога внутри `public` и от Radar с рабочими публикациями. Повторный импорт не создаёт копии тех же учебных событий. Никогда не используйте учебное наполнение для рабочей статистики.

Обычный `npm start` автоматически события не импортирует. В режиме `off` доступны сохранённая история и ручная редакция, опрос внешних источников выключен. Пустая лента в новой базе ожидаема. Для учебного опроса задайте `RADAR_PROVIDER_MODE=mock` в локальной среде; реальных сетевых источников этот режим не использует.

## Настройки среды

Все изменения требуют перезапуска. Булевы значения: `true`/`1`, `false`/`0`; неизвестные значения отклоняются. Секреты хранятся в среде сервера, не в Git и не в браузере.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `RADAR_ENABLED` | `true` | Включает клиентский доступ и задания модуля |
| `RADAR_PROVIDER_MODE` | `off` | `off`, `mock` либо `live` |
| `RADAR_AI_ENABLED` | `false` | Разрешает запросы к настроенному серверному bridge анализа; без endpoint остаются правила |
| `RADAR_AI_ENDPOINT` | пусто | HTTPS-endpoint совместимого JSON-bridge анализа |
| `RADAR_AI_API_KEY` | пусто | Необязательный Bearer-ключ bridge; используется только backend |
| `RADAR_NOTIFICATIONS_ENABLED` | `false` | Разрешает уведомления Radar по персональным правилам |
| `RADAR_MARKET_REACTION_ENABLED` | `true` | Показывает доступную реакцию; встроенный provider создаёт её только для учебных событий |
| `RADAR_ALLOWED_PLANS` | `pro` | Разрешённые тарифы: `pro`, `exclusive` либо `pro,exclusive` |
| `RADAR_FREE_ENABLED` | `false` | Включает ограниченную ленту для вошедших пользователей без разрешённого тарифа |
| `RADAR_FREE_DELAY_SECONDS` | `900` | Задержка FREE, от 60 до 86400 секунд |
| `RADAR_FREE_LIMIT` | `5` | Общий предел доступных FREE-событий, от 1 до 10 |

Каждый производственный источник имеет четыре переменные:

| Источник | Включение | Endpoint | Секрет | Интервал по умолчанию |
| --- | --- | --- | --- | --- |
| Корпоративное раскрытие | `RADAR_EDISCLOSURE_ENABLED` | `RADAR_EDISCLOSURE_ENDPOINT` | `RADAR_EDISCLOSURE_API_KEY` | `RADAR_EDISCLOSURE_INTERVAL=5000` |
| IR компаний | `RADAR_IR_ENABLED` | `RADAR_IR_ENDPOINT` | `RADAR_IR_API_KEY` | `RADAR_IR_INTERVAL=30000` |
| НРД | `RADAR_NSD_ENABLED` | `RADAR_NSD_ENDPOINT` | `RADAR_NSD_API_KEY` | `RADAR_NSD_INTERVAL=60000` |
| Федресурс | `RADAR_FEDRESURS_ENABLED` | `RADAR_FEDRESURS_ENDPOINT` | `RADAR_FEDRESURS_API_KEY` | `RADAR_FEDRESURS_INTERVAL=60000` |

Все `*_ENABLED` изначально `false`, адреса и ключи пустые. Интервалы указаны в миллисекундах; допустимо 1000–3600000. Источник опрашивается только в режиме `live` при собственном разрешении. HTTP-адаптер передаёт непустой ключ как `Authorization: Bearer …`; если официальный API использует иной протокол авторизации, нужен отдельный серверный адаптер.

## Доступ и уведомления

Права проверяются на сервере для страниц, скриптов, API и SSE. По умолчанию полный Radar доступен администратору и действующему Pro. Подписка Exclusive не выдаёт Pro автоматически; изменить состав разрешённых тарифов можно через `RADAR_ALLOWED_PLANS`.

Гость получает запрос входа. FREE выключен по умолчанию; после явного включения вошедший пользователь видит только небольшую задержанную выборку с базовым описанием. Прямые detail-запросы, полный анализ, оценки, реакция рынка, расширенные фильтры, история через cursor, уведомления и SSE требуют полного доступа. FREE допускает только категории `all`, `stocks`, `bonds`; `/api/radar/important` закрыт. Фильтрами нельзя перебрать всю историю через FREE. Задержка учитывает время первоисточника, обнаружения, обработки, публикации и последнего изменения: свежая правка старого сообщения не появляется бесплатно сразу.

Приоритет «Мои компании» объединяет собственные правила Radar с тикерами доступных отслеживаемых идей и личных позиций из существующего кабинета. Связь проверяется через текущие права на идеи: чужой либо уже недоступный ID не раскрывает тикер. Такое включение компании в приоритет не создаёт согласия на отправку уведомлений; для доставки нужны отдельные правила Radar и разрешение канала.

Для Telegram нужны **оба уровня согласия**: персональные правила в Radar и включённый пункт Radar в `/notifications.html` с привязанным Telegram. Также должны быть включены серверный флаг Radar и существующая интеграция Telegram. Низкоприоритетные события ниже 6 не отправляются; порог по умолчанию — 9. Старая история до подписки не рассылается. Перед доставкой повторно проверяются доступ, действующие правила и видимость события.

Браузер запрашивает разрешение уведомлений только после нажатия соответствующей кнопки. Такая доставка работает при открытой странице Radar; Service Worker и фоновый Web Push не реализованы. SSE передаёт только номер ревизии, после чего клиент заново получает разрешённые данные. Сервер повторно проверяет живой сеанс и подписку; истечение доступа завершает соединение. Ограничены число одновременных потоков, срок соединения и объём ответа.

## Подключить первый настоящий источник

1. Получить доступ к официальному API/RSS и определить разрешённую частоту опроса. В репозитории нет выдуманных production-адресов или ключей.
2. Если источник отдаёт совместимый JSON/RSS/Atom, настроить соответствующий `*_ENDPOINT`, разрешение и интервал. Для нестандартного формата добавить адаптер в `lib/radar/providers`, возвращающий `{events, cursor}`; зарегистрировать его в `createProviderRegistry`. Frontend не меняется.
3. В JSON-bridge привести сообщение к контракту ниже. `provider`, `sourceType`, `detectedAt` и признак реального источника назначает серверный адаптер. `externalId` должен быть стабильным, а `sourceUrl` — ссылкой на сообщение, а не платёжным или произвольным внутренним endpoint.
4. Проверить сопоставление компании, несколько источников одного события, повтор импорта, неоднозначное название, ошибочный пакет и восстановление после отказа. После этого включать `RADAR_PROVIDER_MODE=live` для одного источника.

Пример **структуры** bridge-ответа; это не реальное раскрытие:

```json
{
  "events": [{
    "externalId": "stable-message-id",
    "publishedAt": "2026-10-30T09:00:00.000Z",
    "sourceUrl": "https://www.e-disclosure.ru/",
    "title": "Пример корпоративного сообщения",
    "rawText": "Текст официального сообщения без исполняемого HTML.",
    "companyName": "ПАО Сбербанк",
    "ticker": "SBER",
    "isin": "RU0009029540",
    "assetType": "stock"
  }],
  "cursor": "opaque-provider-cursor"
}
```

Пакет — максимум 100 сообщений, ответ — максимум 1 MiB. Поддерживаются JSON-массив, объект с `events` и необязательным `cursor`, а также ограниченный RSS/Atom. Переходы HTTP 3xx, сжатые ответы и XML с DTD/entities отклоняются. Сетевой запрос ограничен таймаутом; DNS проверяется перед соединением и используется непосредственно TLS-соединением. Разрешены публичные HTTPS-адреса без credentials и нестандартного порта; loopback, локальные и приватные сети запрещены. Endpoint и cursor не могут перенаправить запрос во внутреннюю сеть.

Для компании конфигурация хранит `id`, имена/aliases, тикер, ISIN, сектор, активность и поля `irUrl`, `newsUrl`, `investorRelationsUrl`, `providerType`. Исходный каталог находится в `lib/radar/model.mjs`; URLs не заполнены вымышленными адресами. `ПАО Сбербанк`, `Сбер`, `SBER` сопоставляются одному эмитенту; `VTB` — alias тикера `VTBR`. Неоднозначное сообщение сохраняется в черновиках для редакции, а не публикуется с предположенной компанией. Отдельного публичного редактора справочника компаний в этой версии нет.

## Анализ, ожидания и реакция

`RadarAnalysisService` отделён от pipeline. Без настроенного bridge штатный запуск использует рабочие правила классификации, извлечения, оценки и объяснения с `analysisMethod=rules`. Реализован backend-адаптер `createConfiguredAnalysis`: для подключения собственного сервиса анализа задайте `RADAR_AI_ENABLED=true`, публичный HTTPS `RADAR_AI_ENDPOINT` и, если нужен, `RADAR_AI_API_KEY`. Конкретный AI-провайдер, endpoint и действующий ключ в проекте не заданы. Ключ передаётся только сервером в `Authorization: Bearer …`; такой bridge может отдельно обращаться к выбранной владельцем модели.

Bridge получает POST JSON следующей структуры:

```json
{
  "task": "radar-analysis",
  "input": {
    "title": "Заголовок источника",
    "rawText": "Текст сообщения",
    "company": {"id": "sber", "ticker": "SBER"},
    "ticker": "SBER",
    "sourceType": "DISCLOSURE",
    "actualValue": null,
    "expectedValue": null,
    "previousValue": null
  }
}
```

`company` содержит сопоставленную конфигурацию компании целиком либо `null`; сокращённый объект выше показан для ясности. Ответ — `application/json` с объектом RadarAnalysis либо `{ "analysis": RadarAnalysis }`. Обязательные поля анализа: `eventType`, `importanceScore` (0–10), `impact`, `confidence` (0–1), `headline`, `summary`, `whyImportant`, `extractedData`, `tags`. Значения типов и направлений берутся из `lib/radar/model.mjs`; тексты, вложенные данные и дополнительные поля строго проверяются.

Для bridge применяются те же сетевые ограничения, что для источников: публичный HTTPS, проверка DNS и адреса фактического соединения, запрет redirect/private network, таймаут и предел ответа. Ошибка сети или схемы возвращает обработку к правилам. Guard сохраняет извлечённые из источника факты, отклоняет новые числа, неподтверждённые утверждения об ожиданиях и команды BUY/SELL. Это не полная проверка достоверности произвольного текста модели: результат требует редакторского контроля. Не передавайте модельные credentials на frontend.

`actualValue`, `expectedValue`, `previousValue` и `surprisePercent` предусмотрены моделью. Ожидание не придумывается: сравнение появляется только при явно переданном числовом основании. Полноценный consensus-provider пока отсутствует. Значимость и влияние — эвристические оценки, не прогноз цены или гарантия результата.

Интерфейс market-data provider отделён от Radar. `MockMarketDataProvider` формирует цены и изменения 1м/5м/15м/1ч/1д **только для `isDemo=true`**. Реальные сообщения не получают нарисованную реакцию. Для настоящих данных нужен лицензированный источник котировок и планировщик замеров по фактическому времени события; подключение MOEX/AlgoPack здесь не выполнено.

Времена события: `publishedAt` — публикация источника, `detectedAt` — обнаружение сервером, `processedAt` — завершение анализа, `notificationSentAt` — первое подтверждение внешней доставки, если оно было. Последнее не является персональным отчётом о прочтении: отдельные состояния попыток хранятся в существующем outbox. Задержки вычисляются по этим отметкам; демонстрационные значения не являются статистикой скорости продукта.

## API

Все endpoints находятся под существующей авторизацией и проверкой Origin для изменений.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/radar/config` | Режим, доступ пользователя и безопасные флаги без секретов |
| `GET /api/radar/companies` | Активный справочник компаний |
| `GET /api/radar` | Лента `{events,nextCursor,revision}`; без `rawText` |
| `GET /api/radar/important` | Критические события от 9 |
| `GET /api/radar/company/:ticker` | События компании |
| `GET /api/radar/:id` | Полное опубликованное событие для разрешённого тарифа |
| `GET /api/radar/stream` | SSE `ready` / `radar-update` с `{revision}` |
| `GET /api/radar/subscriptions` | Собственные правила отслеживания |
| `POST /api/radar/subscriptions` | Правило `{companyId,eventType,minimumImportance,enabled}`; компания/тип могут быть `null` |
| `DELETE /api/radar/subscriptions/:id` | Удаление только собственного правила |
| `GET /api/admin/radar` | События всех статусов, компании, источники и безопасные ошибки обработки |
| `POST /api/admin/radar` | Ручное событие с `companyId,eventType,headline,summary,whyImportant,impact,importanceScore,source,publishedAt,status` |
| `PATCH /api/admin/radar/:id` | Исправление разрешённых полей с текущей `revision` |
| `DELETE /api/admin/radar/:id` | Отметка дубля с `{revision}`; запись остаётся в базе |
| `POST /api/admin/radar/:id/merge` | Объединение источников: `{revision,targetId,targetRevision}` |
| `POST /api/admin/radar/sync` | Явный опрос разрешённых источников; тело `{}` |

Фильтры ленты: `importance,ticker,company,type,impact,from,to,limit,cursor,q` (либо `search`), `category`, `watchlist=1`. Категории полного доступа: `all,important,stocks,bonds,dividends,earnings,credit,ma`; FREE — только `all,stocks,bonds`. Администратор также может фильтровать `status`. Обычная лента начинается с важности 6; `limit` — 1–50. Cursor привязан подписью к пользователю и фильтрам; после перезапуска процесса нужно начать просмотр заново. `watchlist=1` поднимает компании из правил Radar и доступных отслеживаемых идей/позиций. Приоритет не включает уведомления автоматически и не даёт доступа к чужим данным или к недоступному тарифу.

## Хранилище, сохранность и проверка

Изменение схемы добавочное: приватный `radar.json`, версия 1. Он содержит `companies`, `events`, `subscriptions`, состояния providers, ошибки обработки и общую ревизию. Схемы существующих идей, оплат и аккаунтов не переписываются. Событие содержит несколько `sources`, исходный анализ, audit, trace и доступную market reaction.

Запись атомарная, с блокировкой, контролем ревизии и запретом symlink. Повреждённая база не подменяется пустой. `radar.json` включён в проверку хранилища и зашифрованные резервные копии. После обновления со старой версии создайте новую полную копию; после восстановления проверьте ленту, редакцию, источники и согласия уведомлений.

События не удаляются автоматически. Текущая файловая реализация ограничена 32 MiB для совместимости с резервными копиями, 10 000 событий, 64 источниками на событие и 200 записями его журнала; при достижении предела запись останавливается с ошибкой, история сохраняется. Для постоянного большого потока следующий шаг — миграция Radar в PostgreSQL и отдельные workers, без удаления накопленных данных.

Внешний текст выводится как текст, ссылки проверяются, ключи/ответы провайдеров не публикуются и не попадают в диагностические журналы. SSE содержит только ревизию. Наличие этих мер не заменяет настройку доступа к серверу, TLS, резервных копий и внешнего наблюдения будущего размещения.

Проверка:

```sh
npm test
npm run check:mvp
npm run check:ui
```

Тесты Radar проверяют aliases, классификацию, нормализацию, шум/дедупликацию, безопасные providers, доступ тарифов/FREE, административные изменения, персональные правила, SSE и изоляцию сбоев. Браузерная приёмка проверяет клиентский экран, детали, редакцию, обновления, лендинг и мобильные размеры. Фактические результаты общего запуска фиксируются в отчёте приёмки; реальные источники, AI, котировки и внешняя доставка требуют отдельной проверки после подключения.

## Основные файлы и следующий этап

`lib/radar/model.mjs`, `analysis.mjs`, `pipeline.mjs` — модель и обработка; `providers/` — входящие данные и market-data interface; `service.mjs`, `config.mjs`, `jobs.mjs` — хранение, API, доступ и задания. Интерфейс: `public/radar.html`, `radar-admin.html` и соответствующие assets; учебные данные: `fixtures/radar-events.json`, команда `scripts/seed-radar.mjs`. Существующие server, notifications, backups и локальный запуск интегрируют модуль без второго аккаунтного или UI-стека.

Далее: подключить один настоящий disclosure feed, проверить точность и задержки на реальных сообщениях, затем постепенно добавить IR/НРД/Федресурс. После этого — внешний AI при необходимости, действительные ожидания и котировки, замеры реакции рынка и историческая аналитика. До подключения реальные источники в интерфейсе остаются отключёнными; учебный режим сохраняет явную маркировку.
