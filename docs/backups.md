# Резервные копии и восстановление

Для файловой версии ORBITA предусмотрена команда `scripts/backup.mjs`. Она сохраняет аккаунты, идеи, платежи, очередь уведомлений, уроки/статьи (`content.json`), общие настройки (`product-settings.json`), новостной файл и `.security-key` из `ORBITA_DATA_DIR`. Ключ нужен для расшифровки MFA после восстановления; его нельзя терять отдельно от базы аккаунтов. Все эти базы участвуют в согласованной блокировке снимка; временные файлы проверки готовности не включаются.

Копия содержит обычные файлы каталога данных, включая вложенные. В неё не входят блокировки `*.lock`, временные файлы с `.tmp` в имени, другие `.orbita-backup` и файлы SQLite/Telegram: `.session`, `.sqlite`, `.sqlite3`, `.db` вместе с `-wal`, `-shm`, `-journal`. Символические ссылки и специальные файлы отклоняются. Сессии Telegram нужно сохранять отдельно при остановленном клиенте либо средствами SQLite Online Backup; этот скрипт не заявляет согласованность живой SQLite-базы. Переменные окружения, пароли SMTP, токен Telegram-бота и настройки платёжного провайдера в копию не входят: храните их отдельно в защищённых настройках развёртывания.

На время чтения скрипт получает блокировки `accounts.json.lock`, `ideas.json.lock`, `billing.json.lock`, `notifications.json.lock` и других корневых JSON-файлов. Если хранилище занято, он ждёт до пяти секунд и завершает попытку без частичной копии. Работающие сервер и CLI должны использовать тот же протокол блокировок. Для точного снимка состояния внешнего платёжного провайдера после восстановления нужно выполнить сверку платежей: сетевые операции не входят в файловую транзакцию.

Формат версии 1 использует gzip, scrypt (`N=32768, r=8, p=1`, случайная соль 16 байт), AES-256-GCM со случайным nonce 12 байт и аутентификацией заголовка. Манифест внутри шифрования содержит SHA-256 и размер каждого файла. До восстановления проверяются тег, пути, дубликаты, размеры, контрольные суммы, JSON и размер `.security-key`. Ограничение одной копии — 64 МиБ исходных данных, 32 МиБ на файл и 1000 файлов. При достижении лимита команда завершится ошибкой; перед увеличением нагрузки перенесите данные в БД с её штатным резервным копированием.

## Создать и проверить

Нужен Node.js 20+. Каталог копий должен находиться вне `public` и вне каталога данных, иметь права `0700`. Новые каталоги скрипт создаёт с такими правами; существующие общедоступные каталоги он отклоняет. Архивы создаются с правами `0600`.

```bash
install -d -m 700 /workspace/private-orbita-backups
export ORBITA_DATA_DIR=/workspace/Orbita/data
export ORBITA_BACKUP_DIR=/workspace/private-orbita-backups
read -r -s -p 'Парольная фраза копий: ' ORBITA_BACKUP_PASSPHRASE
export ORBITA_BACKUP_PASSPHRASE
node scripts/backup.mjs create
node scripts/backup.mjs list
node scripts/backup.mjs verify --file /workspace/private-orbita-backups/ИМЯ.orbita-backup
unset ORBITA_BACKUP_PASSPHRASE
```

Используйте отдельную длинную случайную парольную фразу, не менее 16 символов, и сохраните её в менеджере паролей. Скрипт принимает её только через `ORBITA_BACKUP_PASSPHRASE`, не через аргументы CLI, и не выводит её или расшифрованное содержимое файлов. Команда `list` показывает имена и размеры; подлинность копии подтверждается командой `verify`.

`create --keep 14` явно включает очистку: сохраняются 14 самых новых копий с собственным форматом имени. Перед удалением каждой старой копии проверяются пароль и целостность. Посторонние файлы, повреждённые архивы и копии с другой парольной фразой остаются на месте и перечисляются в `retention.skipped`. Без `--keep` ничего не удаляется. Смена фразы не перешифровывает старые копии.

## Расписание

Сервер автоматически создаёт копии только при явном задании `ORBITA_BACKUP_DIR` и `ORBITA_BACKUP_PASSPHRASE`: при старте и затем раз в `ORBITA_BACKUP_INTERVAL_HOURS` часов (24 по умолчанию), с хранением `ORBITA_BACKUP_KEEP` последних проверенных копий (7 по умолчанию). Неуспешная попытка не заменяет предыдущий архив; ошибка отмечается в stderr без секретов. Проверяйте журнал и дату последней копии. При размещении вне сервера или для независимого расписания используйте CLI.

CLI сам не устанавливает cron и ничего не загружает в облако. Вместо встроенного расписания администратор может добавить ежедневный запуск в системное расписание. Например, сохраните переменные в отдельном файле `/workspace/private-orbita-backups/backup.env` с правами `0600` и задайте cron:

```cron
15 3 * * * /bin/bash -c 'set -a; source /workspace/private-orbita-backups/backup.env; set +a; cd /workspace/Orbita && /usr/bin/node scripts/backup.mjs create --keep 14' >> /workspace/private-orbita-backups/backup.log 2>&1
```

В `backup.env` задаются `ORBITA_DATA_DIR`, `ORBITA_BACKUP_DIR` и `ORBITA_BACKUP_PASSPHRASE`. Настройте часовой пояс cron на нужный часовой пояс, например `Europe/Moscow`; проверьте реальный путь к Node.js командой `command -v node`. Ограничьте права журнала до `0600`, следите за кодом завершения и свободным местом. Не храните файл с фразой вместе с копиями на общем носителе: пример пути удобен для локального запуска, а фразу для восстановления следует хранить отдельно. Для защиты от потери диска перенесите уже зашифрованные копии на отдельный приватный носитель своим штатным средством и регулярно проверяйте восстановление.

## Безопасное восстановление

Команда требует явного `--restore`. Она полностью расшифровывает и проверяет архив до записи файлов, создаёт закрытый временный каталог рядом с назначением и публикует готовый каталог одним `rename`. Существующие данные не перезаписываются. При ошибке временный каталог удаляется; пустой каталог назначения восстанавливается, если был удалён перед неудачным финальным переименованием.

```bash
node scripts/backup.mjs verify --file /workspace/private-orbita-backups/ИМЯ.orbita-backup
node scripts/backup.mjs restore --file /workspace/private-orbita-backups/ИМЯ.orbita-backup --restore /workspace/orbita-restored
```

Каталог `/workspace/orbita-restored` должен отсутствовать либо быть пустым и не находиться в `public`. Данные восстанавливаются вместе с `.security-key`; не подменяйте этот ключ ключом от другой среды. Команда не переключает живой сервер на восстановленный каталог. После проверки остановите сервер и фоновые обработчики, сохраните прежний каталог, задайте новый `ORBITA_DATA_DIR` и запустите сервер. Проверьте вход администратора, MFA, идеи, подписки, очередь уведомлений и сверку платежей до возобновления обработки. Сессии и токены из старого снимка могут быть неактуальны: после аварийного восстановления завершите активные сессии и отзовите лишние одноразовые ссылки.

Резервная копия содержит персональные данные и секретный ключ, даже когда она зашифрована. Ограничьте доступ к копиям и парольной фразе, не добавляйте их в Git и не размещайте в публичном каталоге сайта.
