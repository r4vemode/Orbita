# ORBITA — защита MVP

Состояние на 30 октября 2026 года. Это описание реализованных мер и границ проверки, а не гарантия отсутствия уязвимостей. Приложение рассчитано на один процесс с приватным постоянным диском. Размещение пока отложено владельцем.

## Что уже защищает данные и доступ

- Сервер проверяет сессию, действующую подписку и роль на страницах, закрытых скриптах и API. Pro и Exclusive независимы; публичные страницы стратегий не отдают платные идеи. Отзыв и истечение учитываются в существующей сессии.
- Пароли хранятся как scrypt-хеш с индивидуальной случайной солью. Cookie сессии — HttpOnly/SameSite; при публичном HTTPS добавляется Secure. Токены подтверждения и восстановления одноразовые, ограничены по времени, в базе хранится их хеш. Сброс пароля отзывает сессии и старые ссылки.
- Администратор на публичном HTTPS проходит MFA с одноразовыми резервными кодами. Отключение обязательной MFA через настройку останавливает публичный сервер. Назначение первого администратора выполняется доверенной локальной командой, а не формой регистрации.
- Публикация юридических документов дополнительно требует текущего пароля и свежего второго фактора, если он включён. После проверки пароля сервер повторно проверяет живую сессию, роль и хеш пароля внутри транзакции; один резервный код или TOTP нельзя использовать повторно. Действуют отдельные ограничения попыток. Сохранённая cookie сама по себе не разрешает публикацию.
- Изменяющие запросы браузера требуют точный Origin. Исключения — конкретные callback провайдеров с собственной проверкой подписи или секрета. CloudPayments проверяет исходные байты, сумму, аккаунт, режим и повторные уведомления; карточные данные вводятся у провайдера.
- Публикации выводятся как текст с экранированием. CSP запрещает сторонний и встроенный JavaScript, встраивание сайта во фрейм и подмену базового URL. Добавлены ограничения доступа к ресурсам из других origin, отключение ненужных возможностей браузера и HSTS для HTTPS.
- Данные, ключ MFA и зашифрованные копии находятся вне `public`; скрытые файлы и каталоги вроде `.env` и `.git` закрыты даже при случайном попадании в публичную папку. Чувствительные ответы не кешируются. Неожиданные ошибки получают безопасный код обращения; пароли, cookie, тела запросов и токены в диагностический журнал не выводятся.

## Документы, согласия и рабочие продажи

Черновик реквизитов и его предпросмотр закрыты правами администратора. Публичные страницы получают только опубликованную редакцию либо исходные проекты документов; частично сохранённые поля не публикуются. ИНН/ОГРН проверяются по формату и контрольным цифрам, значения экранируются в HTML. Это не проверка сведений в реестре или юридическое заключение.

Публикация сохраняет полный HTML оферты, политики и возвратов, дату, автора и номер редакции. Последующие шаблоны не меняют сохранённые тексты, публичный API не позволяет удалять историю. Регистрация сохраняет фактически принятую версию; если она изменилась при заполнении формы, сервер отвечает 409 и требует заново подтвердить согласия. Прежние согласия аккаунтов сохраняются. Новый рабочий заказ также фиксирует редакцию оферты, а повтор с тем же идентификатором не подменяет условия первоначального заказа.

Ключи CloudPayments не открывают рабочие продажи автоматически: нужны опубликованные документы, `ORBITA_LIVE_PAYMENTS_ENABLED=true` и `ORBITA_RECEIPTS_CONFIRMED=true`. Последний флаг — подтверждение оператором подготовленного чекового процесса, а не реализация кассы или проверка фактического чека. При закрытых продажах новые заказы и Check отклоняются, но подписанные Pay/Refund продолжают обрабатываться для уже проведённых операций. Настройка Check у провайдера обязательна; закрытие продаж в Orbita само по себе не отменяет ранее созданные счета в CloudPayments.

`legal.json` проходит проверку структуры и контрольных сумм и входит в согласованные зашифрованные копии. Эти суммы обнаруживают повреждение, но не защищают от администратора файловой системы, способного изменить и данные, и суммы. Порядок публикации и ограничения — в [legal-documents.md](legal-documents.md).

## Ограничение злоупотреблений

Общие лимиты применяются к API до чтения базы и тела запроса:

| Мера | Значение |
| --- | --- |
| Чтение API | 600 запросов за минуту на адрес клиента |
| Изменения API | 60 запросов за минуту на адрес клиента, включая неуспешные обращения |
| Одновременные запросы одного клиента | 8 |
| Одновременные обычные API-запросы | 32 |
| Отдельная ёмкость callback провайдеров | 8, чтобы обычные запросы не занимали все слоты |
| Тело запроса | до 64 КиБ, для создания оплаты — 16 КиБ |
| Абсолютное время чтения тела | 10 секунд, медленная передача завершается ответом 408 |
| HTTP-заголовки / общий запрос | 15 / 20 секунд; заголовки до 16 КиБ |
| Вычисления паролей | 2 активных, 8 ожидающих; ограниченное время ожидания |

Запросы с неверным Origin отклоняются ещё раньше, не читая базу и тело. Отдельно сохраняются более строгие ограничения входа, регистрации, сброса и MFA по адресу и аккаунту/токену. Карты счётчиков имеют верхний предел; живое ограничение нельзя вытеснить новым ключом. Несуществующая ссылка сброса не запускает scrypt. Валидный сброс после вычисления снова проверяет токен и прежний пароль внутри транзакции.

Ответы 429/503 сообщают о перегрузке, общий лимитер возвращает Retry-After. Ранняя ошибка загрузки или отказ в приёме закрывает соединение после ответа. Завершение и обрыв освобождают слот ровно один раз. Лимиты находятся в памяти одного процесса и сбрасываются при перезапуске; это не распределённая защита от DDoS.

За обратным прокси адрес клиента определяется только при соединении с IP из `ORBITA_TRUSTED_PROXY_IPS`. Цепочка X-Forwarded-For разбирается справа до первого недоверенного узла. Заголовки обычного клиента игнорируются. Значения подтверждаются при настройке размещения; локально поле пустое. Нельзя подставлять произвольные адреса или настраивать прокси на слепую передачу присланного клиентом заголовка.

## Radar

Страницы, скрипты, лента, полный разбор, правила и SSE проверяют доступ на сервере. FREE выключен по умолчанию; ограниченная выборка при включении задерживается по серверным временам появления и изменения события. Через фильтры нельзя перебрать всю историю или получить полный анализ. SSE передаёт только ревизию, ограничивает соединения и повторно проверяет живой сеанс и тариф.

Внешние запросы выполняет только backend: HTTPS, проверка и закрепление публичного DNS-адреса в TLS-соединении, запрет внутренних/переходных IP, credentials в URL и редиректов, ограничения времени и размера. HTML/XML обрабатываются ограниченными линейными проходами; исполняемая разметка не попадает в DOM. Отмена задания доходит до анализа и сетевого запроса; ошибка источника не останавливает остальные.

Уведомления требуют действующего доступа, явных правил, серверного разрешения и отдельного согласия на Telegram. Перед повторной доставкой проверяются отзыв доступа, отказ от отслеживания и скрытие события. Ручная отметка дубля остаётся в истории и подавляет повторный импорт исходного сообщения. Подробности и границы — в [radar.md](radar.md) и [отчёте проверки](radar-acceptance-2026-10-30.md).

## Что сделать при выборе размещения

1. Использовать актуальную поддерживаемую LTS-версию Node.js, рекомендуется 24 LTS. Node 20 завершил поддержку 30 апреля 2026 года по [официальному расписанию](https://github.com/nodejs/Release/blob/main/schedule.json); минимум проекта повышен до 22. Минимальная версия сама по себе не заменяет установку свежих исправлений.
2. Закрыть внешний доступ к порту Node.js. Оставить наружу HTTPS-прокси с ограничениями соединений и фильтрацией/WAF; подключить защиту от объёмных атак у размещения или внешнего сервиса.
3. Запускать приложение под отдельным пользователем без root, хранить ключи в секретах среды, защитить аккаунты домена, GitHub, хостинга, почты и CloudPayments двухфакторной аутентификацией.
4. Держать зашифрованную копию вне основного сервера и проверить восстановление. Следить за ошибками, отказами входа, всплесками 429 и задержкой выдачи доступа после оплаты.
5. Пройти `npm run preflight -- --production`, реальный платёжный цикл и проверки публичного адреса. Затем провести отдельную проверку безопасности внешнего стенда: текущий локальный прогон не проверяет будущую сеть и конфигурацию прокси.

Настройка хостинга и подключение внешних служб этим документом не выполняются. Владелец по-прежнему заполняет реквизиты, поддержку и реальные ключи отдельно.

## Проверить изменения локально

```sh
npm test
npm run check:mvp
npm run beta:local
```

Тесты проверяют доступ без подписки и после отзыва, MFA и токены, повторное подтверждение публикации, смену редакций и закрытие продаж с сохранением обработки Pay/Refund, подделку адреса клиента, исчерпание лимитов, медленные/большие тела, обрыв соединения, неизменность подписываемых байтов и гонку сброса пароля. Воспроизведённый поток из 160 одинаковых изменений больше не приводит к 160 записям; чтение аккаунта и health остаются доступны. Реальные провайдеры не вызываются. Это целевые проверки и регрессии, не независимый пентест.
