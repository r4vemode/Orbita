# ORBITA — подготовка VPS

Пакет рассчитан на один VPS с Ubuntu 24.04 LTS: **2 vCPU, 4 ГБ RAM, от 40 ГБ SSD**, публичный IP и домен. Это начальный размер для закрытой беты, а не измеренная ёмкость рабочего сервиса. Файловая база использует один экземпляр приложения и постоянный локальный диск.

Сервер ещё не выбран. Эти файлы подготавливают запуск, но не создают VPS, DNS, магазин CloudPayments или почтовый домен. Никакие ключи, реквизиты и адреса поддержки не подставлены заранее.

## Что входит в пакет

- `Dockerfile`: Node.js 24 LTS, зафиксированный digest образа, непривилегированный пользователь UID/GID 1000, только рабочие исходники и операционные CLI. Установка npm-пакетов для запуска не нужна.
- `compose.yaml`: наружу публикуются только HTTP/HTTPS Caddy; порт Node.js 3000 не публикуется. Приложение имеет read-only корневую систему, временный `/tmp`, ограничения ресурсов и отдельные приватные каталоги данных/копий.
- `Caddyfile`: автоматический HTTPS для выбранного домена, сохранение сертификатов в именованных томах, замена присланного клиентом `X-Forwarded-For`, передача потока Radar без накопления ответа.
- `.env.example`: параметры без реальных значений. Приём рабочих оплат и внешние источники выключены.

## 1. Выбрать сервер и домен

Используйте VPS с постоянным локальным диском и доступом по SSH-ключу. Узнайте у провайдера порядок снимков диска и восстановления. Управление аккаунтом провайдера защитите MFA. Закрытый SSH-ключ остаётся на вашем компьютере.

В DNS создайте `A` для выбранного имени с IPv4 сервера. `AAAA` добавляйте только после фактической настройки IPv6 на этом VPS. Уберите ошибочную `AAAA`, если она ведёт на другой сервер: она мешает подключению клиентов и выдаче сертификата.

Во внешнем firewall провайдера разрешите SSH только со своего административного адреса, а TCP 80/443 и UDP 443 — для сайта. Не открывайте 3000 или Docker API. На первом этапе Caddy должен получать запросы непосредственно, без ещё одного CDN/прокси: для дополнительного прокси нужно отдельно настроить доверенную цепочку адресов.

## 2. Подготовить Ubuntu

Установите обновления ОС, создайте отдельного административного пользователя с SSH-ключом и проверьте вход во второй сессии перед изменением доступа к SSH. Установите Docker Engine и Compose plugin по [официальной инструкции Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/).

Проверьте:

```sh
sudo docker version
sudo docker compose version
```

Не добавляйте непроверенных пользователей в группу `docker`: доступ к Docker фактически даёт управление сервером. Публикация контейнерных портов может обходить обычные правила UFW; здесь публикуются только порты Caddy. Правила firewall провайдера проверяются отдельно для IPv4 и IPv6.

Подготовьте каталог исходников, принадлежащий текущему административному пользователю:

```sh
sudo install -d -m 0755 /srv/orbita
sudo install -d -m 0755 -o "$(id -u)" -g "$(id -g)" /srv/orbita/app
```

Распакуйте полный проект или получите проверенный release в `/srv/orbita/app`. Следующие команды выполняются из этой папки. Если выбран иной каталог, сохраняйте ту же структуру проекта.

## 3. Подготовить приватные данные и настройки

```sh
sudo install -d -m 0700 -o 1000 -g 1000 /srv/orbita/private
sudo install -d -m 0700 -o 1000 -g 1000 /srv/orbita/private/data
sudo install -d -m 0700 -o 1000 -g 1000 /srv/orbita/private/backups
umask 077
cp deploy/.env.example deploy/.env
chmod 600 deploy/.env
chmod 644 deploy/Caddyfile
```

`1000:1000` — пользователь Node внутри контейнера. Команда `chmod 777` не нужна. `Caddyfile` содержит только несекретную конфигурацию и должен читаться контейнером с урезанными capabilities; его права 0644 не применяются к `.env`, данным или копиям. Если переносите существующую базу, сначала остановите её прежний процесс и сохраните отдельную копию. Переносите весь приватный каталог, включая `.security-key`, затем проверьте владельца и права. Не смешивайте рабочую базу с учебным импортом и не запускайте её одновременно из двух мест.

В `deploy/.env` укажите:

- `ORBITA_DOMAIN`: имя сайта без `https://`, пути, порта и wildcard.
- `ORBITA_BACKUP_PASSPHRASE`: уникальная случайная фраза от 16 символов. Сгенерируйте её локально, например `openssl rand -base64 48`, и сохраните вторую копию в менеджере паролей отдельно от архивов.
- `ORBITA_DATA_PATH` и `ORBITA_BACKUP_PATH`, если отличаются от подготовленных выше путей.

Реальные поддержку, почту, магазин и Telegram можно добавить позже согласованными наборами настроек. Значения с `$`, `#` или пробелами заключайте в одинарные кавычки по формату Docker env file. Не публикуйте `.env`, вывод `docker inspect` с окружением или полный `docker compose config`: там могут оказаться ключи. Для проверки используйте `config --quiet`.

Compose требует домен и фразу резервного копирования до старта. Автоматические зашифрованные копии создаются при запуске и затем каждые 24 часа; сохраняются последние 7 корректных собственных копий. Каталог копий находится на том же VPS: дополнительно перенесите зашифрованную копию во внешнее приватное хранилище и проверьте восстановление. Локальная копия сама по себе не защищает от потери всего VPS.

## 4. Проверить конфигурацию и запустить

Для краткости создайте функцию текущего терминала:

```sh
orbita_dc() { sudo docker compose --env-file deploy/.env -f deploy/compose.yaml "$@"; }
orbita_dc config --quiet
orbita_dc build --pull app
orbita_dc up -d
orbita_dc ps
orbita_dc logs --tail=50 app
```

Caddy начнёт выдачу публичного сертификата после правильного DNS и доступности портов 80/443. Режим HTTPS принудительно требует MFA администратора. Node.js принимает запросы только внутри Docker-сети; его порт не нужно публиковать для настройки.

Сеть использует `172.30.87.0/29`: Caddy имеет `172.30.87.2`, приложение — `172.30.87.3`. Приложение доверяет **только точному адресу Caddy**, а прокси заменяет входящий `X-Forwarded-For` реальным адресом непосредственного клиента. Если эта подсеть занята на VPS, выберите свободную приватную подсеть и согласованно измените `subnet`, оба `ipv4_address` и `ORBITA_TRUSTED_PROXY_IPS` в `compose.yaml`. Не заменяйте точный адрес на `*` или всю сеть.

Проверки после запуска:

```sh
curl --fail https://ВАШ-ДОМЕН/healthz
curl --fail https://ВАШ-ДОМЕН/readyz
orbita_dc exec app node scripts/preflight.mjs
```

`/readyz` проверяет хранилище, а не готовность магазина и доставки писем. Healthcheck контейнера использует этот путь; unhealthy сам по себе не перезапускает контейнер в обычном Docker Compose. Следите за состоянием через отдельное внешнее наблюдение и журналы. Политика `unless-stopped` перезапускает завершившийся процесс, но не исправляет неверные ключи или повреждённую базу.

## 5. Создать своего администратора

1. Зарегистрируйте свой аккаунт на сайте по HTTPS.
2. В том же каталоге проекта назначьте зарегистрированной почте роль:

```sh
orbita_dc exec app node scripts/manage-access.mjs admin ВАША-ПОЧТА
```

3. Откройте `/admin.html`, настройте MFA в разделе безопасности и сохраните резервные коды в менеджере паролей. Привилегии редакции станут доступны после подключения защиты.
4. Заполните автора, контакт поддержки и документы. Старый локальный персональный установщик `admin-download` для VPS не используется и в образ не включён. Email новым назначением не отмечается подтверждённым.

Для закрытой беты администратор может вручную выдавать тестовый доступ отдельным клиентским аккаунтам. Не выдавайте тестировщикам административную роль.

## 6. Отдельно допустить реальные продажи

Первый технический запуск работает с пустыми интеграциями и закрытыми продажами. Не используйте строгий preflight как entrypoint контейнера: до заполнения документов и внешних настроек он должен показать незавершённые пункты, оставляя доступной настройку сайта.

После подключения и проверки реальных писем, CloudPayments, документов и чекового процесса заполните в `deploy/.env` реальный `ORBITA_SUPPORT_EMAIL` вместе с согласованными параметрами почты и магазина. Этот контакт требуется CLI-проверке даже при уже указанном адресе в настройках интерфейса. После изменения окружения пересоздайте приложение, затем выполните:

```sh
orbita_dc exec app node scripts/preflight.mjs --production
```

До открытия продаж должны пройти реальные регистрация/восстановление на этом домене, тестовая оплата, независимость Pro/Exclusive, выдача/отзыв доступа и контрольный возврат. `ORBITA_RECEIPTS_CONFIRMED=true` — подтверждение оператором проверенного порядка чеков, а не подключение кассы. Не меняйте два разрешающих флага просто для получения зелёного отчёта. Пока внешние условия не выполнены, сохраните `ORBITA_LIVE_PAYMENTS_ENABLED=false` и `ORBITA_RECEIPTS_CONFIRMED=false`.

После изменения `.env` пересоздайте приложение: `orbita_dc up -d --force-recreate app`. Caddy admin API выключен; после изменения `Caddyfile` восстановите его несекретные права командой `chmod 644 deploy/Caddyfile`, затем применяйте `orbita_dc restart caddy`. Редактор или получение нового release при `umask 077` может снова создать файл с правами 0600.

## Копии, обновление и откат

Перед обновлением:

```sh
orbita_dc exec app node scripts/backup.mjs create
```

Сохраните имя копии и текущий commit/release проекта. Проверка копии: `orbita_dc exec app node scripts/backup.mjs verify --file /var/backups/orbita/ИМЯ-КОПИИ`. После переноса зашифрованного файла вне VPS проверьте его там той же версией проекта; фраза шифрования передаётся отдельно.

Образы Node и Caddy закреплены digest. Новые исправления безопасности попадают в проверенный release после обновления этих digest и повторных тестов; `pull` старого digest не обновляет его содержимое автоматически. Не ставьте непроверенный автоматический обновлятор поверх рабочего приложения.

Обновите исходники до выбранного release, выполните `chmod 644 deploy/Caddyfile` и `orbita_dc build --pull app`, затем `orbita_dc up -d --no-deps app` и повторите проверки. Если менялся прокси, перезапустите Caddy после проверки его конфигурации. Compose не должен запускать две реплики Orbita. Не удаляйте приватные каталоги и не выполняйте `down -v`: это удалит тома сертификатов.

Для отката остановите приложение, верните прежний проверенный release и его образ. После изменения формата данных не запускайте старый код поверх новой базы: восстановите проверенную копию в **новый пустой** приватный каталог, проверьте её и только затем переключите `ORBITA_DATA_PATH`. Порядок восстановления — в [backups.md](../docs/backups.md). Рабочая база не перезаписывается командой restore.

## Границы проверки

Локально собран и запущен образ с Node.js **24.22.2**, закреплённым указанным digest. В изолированном контейнере без опубликованных портов проверены UID 1000, read-only код, приватный ключ MFA, HTTPS-origin и Secure cookie, назначение администратора с обязательной MFA, закрытые продажи, зашифрованная копия с проверкой/восстановлением, штатная остановка и сохранение сессии/MFA после перезапуска. Для теста использованы только вымышленные аккаунты и временные каталоги.

Образ Caddy **2.11.7** получен по закреплённому digest; его адаптер разобрал рабочий `Caddyfile`. Публичный сертификат для настоящего домена этой проверкой не выпускался.

Отдельный локальный HTTP-стенд с тем же Caddy проверил замену поддельного `X-Forwarded-For`, правильный `Host` upstream и получение первого SSE-фрагмента до завершения потока. Это проверка прокси на фиктивном upstream, а не подключение реального биржевого источника.

Это не заменяет проверку выбранного VPS: DNS, публичного сертификата, firewall, SSH-доступа, провайдера диска, внешних копий, настоящей почты и платежей. Перед приглашением клиентов пройдите эту проверку на фактическом домене и устройствах участников.
